# ADR 0035: Reproducible capacity and performance benchmark

- Status: Accepted
- Date: 2026-07-27

## Context

Issue #50 asked for reproducible measurements across 8 named dimensions (decision throughput and
latency, policy evaluation cost, persistence latency, outbox publish throughput, replay throughput,
database growth and index impact, connection-pool saturation, audit/hash-chain overhead),
documented with environment, dataset size, warm-up, configuration, p50/p95/p99, error rate, at
least one identified bottleneck, and reproduction commands. roadmap.md's Gate 7 exit criterion
states this directly: "capacity claims include environment and p50/p95/p99 evidence" -- the same
bar the issue's own acceptance criteria set, so unlike several earlier issues this session (e.g.
ADR 0034 for #54), there was no scope-narrowing decision to make: all 8 dimensions are genuinely
measurable against this system's current, real implementation, with no signal-model or
architectural gap blocking any of them.

This repository has never published a capacity number before. Every other "report, don't gate"
precedent this session established (JaCoCo coverage in ADR 0031, jqwik property counts in ADR
0033) applies here too: numbers are reported as CI/nightly artifacts, never hardcoded into
documentation (which would go stale immediately) and never asserted against a hard pass/fail
threshold this codebase has no historical baseline to justify.

## Decision

### One harness, reused across 6 test classes

A shared `BenchmarkStats` (latency samples -> p50/p95/p99/mean/min/max/throughput/error-rate) and
`BenchmarkReport` (Markdown rendering, with an environment section: Java version, OS, available
processors, max JVM heap, database) live in a new `benchmark` test-support package, `public` so
every dimension's test class can reuse them regardless of which package it needs to live in for
module-internal access. See `docs/operational/capacity-benchmark.md` for the full
dimension-to-test-class mapping and package-placement reasoning (3 of the 8 dimensions need direct
`internal`-package repository/relay access, matching the existing internal-module-test convention
rather than exposing those internals outside their module).

### Real Spring context, real Postgres, no hardcoded numbers

Every dimension runs against the real `ProtectionDecisionService`, `PolicyEvaluationService`,
`SimulationService`, `AuditChainVerificationService`, `ProtectionRequestRepository`, and
`OutboxRelay` -- the same production code paths every other integration test in this codebase
exercises, via Testcontainers Postgres. No dimension is measured against a mock or an
in-memory stand-in that would make the number meaningless.

### Default-gate smoke test vs. nightly measurement-grade suite

Following ADR 0032's exact `@Tag("resilience")` precedent, every measurement-grade benchmark class
is `@Tag("benchmark")`, excluded from `ci.yml`'s default gate
(`-DexcludedGroups=resilience,benchmark`) and run in full every night (`nightly.yml`, which passes
no `-DexcludedGroups`). A small, untagged `CapacitySmokeBenchmarkTest` (10 sequential `decide()`
calls) runs in the default gate on every PR, asserting only that the harness completes without
error -- directly satisfying "CI runs a smoke benchmark without flaky hard thresholds": a shared
CI runner's timing is too noisy to gate a PR on a specific millisecond number, but the harness
itself running correctly is exactly the kind of thing that should never silently rot.

### The required "at least one measured bottleneck"

`ConnectionPoolSaturationTest` is built specifically to produce this reliably and reproducibly: its
own Spring context shrinks `spring.datasource.hikari.maximum-pool-size` to 3 via
`@DynamicPropertySource` (the same per-test datasource-override pattern
`DatabaseLatencyResilienceTest` already established for Toxiproxy, ADR 0032), then compares
decision latency at concurrency == pool size against concurrency = 4x pool size. Connection-pool
contention is a real, directly attributable, and safely bounded (default 5s `connection-timeout`,
generous headroom over this workload's actual per-call latency) bottleneck -- not a flaky
failure-injection scenario, a genuine, honest latency-growth measurement.

### Bounded, deterministic-shape seeding

Every dimension uses bounded iteration counts (tens to low thousands, not open-ended) chosen to
keep the nightly run's added wall-clock time small while still producing a real trend: decision
throughput uses 150 sequential + 100 concurrent calls; database growth uses 3 cumulative row-count
tiers (500/2,000/8,000) via `saveAndFlush`, deliberately modest to keep the nightly run bounded
while still showing a real growth trend for the primary-key index; connection-pool saturation uses
30 calls per phase. Signal inputs are generated by a simple deterministic function of loop index
(not random), so a re-run's *distribution* of decision outcomes is reproducible even though the
absolute timing numbers are not (see "wall-clock, not statistically isolated" below).

## Alternatives considered

- **JMH** (Java Microbenchmark Harness) -- rejected: JMH benchmarks are typically standalone,
  isolated from the Spring context and a real transactional database, which is exactly what this
  codebase's actual cost drivers (policy lookup, audit-chain append, envelope encryption, real
  connection-pool contention) depend on. A JMH microbenchmark of, say, risk-score arithmetic in
  isolation would answer the wrong question. Bringing up a full `@SpringBootTest` context per JMH
  fork is possible but adds a second, heavier build-tool integration for marginal benefit over
  reusing this codebase's existing JUnit-based Testcontainers integration-test infrastructure.
- **A dedicated load-testing tool (k6, Gatling)** -- rejected for the same core reason plus a new
  external dependency and a second language/DSL, disproportionate to a Spring Modulith monolith
  that already has a full integration-test harness capable of measuring the same code paths
  directly.
- **Hardcoding a published number in this documentation** -- rejected: no historical baseline
  exists for this codebase, hardware varies between CI, nightly, and any reader's own machine, and
  a stale hardcoded number is worse than no number at all (mirrors ADR 0031's identical reasoning
  for deferring a JaCoCo coverage threshold).
- **A JMeter/HTTP-level load test against the running Docker image** -- considered as a way to
  measure the true end-to-end HTTP path including the smoke-tested container from ADR 0031, but
  rejected for this issue: it would require standing up the full image plus a separate load-driving
  tool in CI, a materially larger addition than reusing the existing Testcontainers-based
  integration-test infrastructure, for numbers that would still ultimately bottleneck on the same
  application-layer code this ADR already measures directly.

## Consequences

### Positive

- every one of issue #50's 8 named dimensions is genuinely measured against real production code
  paths, not simulated or mocked;
- the harness is a normal JUnit test suite reusing this codebase's existing Testcontainers
  infrastructure -- no new build tool, no new external dependency;
- numbers are always fresh (regenerated every PR/night) and always environment-labeled, so they can
  never silently drift out of sync with the code that produced them;
- the connection-pool saturation test gives a reliable, reproducible, non-flaky "measured
  bottleneck" without needing a real production incident to observe one.

### Negative

- numbers are single wall-clock runs on shared CI/nightly hardware, not statistically rigorous,
  isolated, warmed-up benchmarks -- explicitly labeled as directional, not SLA-grade, in every
  report;
- database growth is tested only up to 8,000 rows (bounded for nightly runtime), far below a
  realistic production data volume -- a real large-scale growth curve would need a separate,
  longer-running, dedicated exercise;
- the benchmark reports are Markdown artifacts, not a persisted historical time series --
  regression-over-time tracking (e.g. "p95 grew 30% since last month") is not implemented.

## Guardrails

- Every benchmark test class was run locally against a real Testcontainers Postgres instance before
  this PR (Docker was available in this environment for this issue, unlike several earlier issues
  this session) -- all 5 classes (`CapacityBenchmarkTest`, `PersistenceLatencyBenchmarkTest`,
  `OutboxPublishThroughputBenchmarkTest`, `ConnectionPoolSaturationTest`,
  `CapacitySmokeBenchmarkTest`) passed with real, sane-looking numbers, and the generated Markdown
  reports were manually inspected.
- A real locale-formatting bug was caught during that local verification: `String.format("%.2f", ...)`
  without an explicit `Locale` rendered numbers with comma decimal separators on this machine's
  default locale (e.g. `25,39 ms`), which would have produced environment-dependent, inconsistently
  formatted reports between a non-US-locale local run and CI's runner. Fixed by passing
  `Locale.ROOT` explicitly everywhere a number is formatted.
- No benchmark asserts a specific latency/throughput number; every assertion is either "zero errors"
  or (for the audit-chain benchmark) "the chain verification result reports valid" -- correctness
  guardrails, never performance gates, consistent with this ADR's "report, don't gate" stance.

## Revisit criteria

- Once this codebase has a real historical baseline (a few weeks of nightly numbers), consider
  persisting them as a time series (even a simple CSV artifact per run) so regressions can be
  tracked automatically rather than only compared by a human reading two Markdown files.
- If a real production capacity-planning need arises, extend the database-growth tiers well beyond
  8,000 rows and run on dedicated (non-shared-CI) hardware for SLA-grade numbers.
- If the HTTP/container-level path (not just the application-layer service calls this ADR measures)
  ever needs its own capacity number, revisit the JMeter/k6-against-the-Docker-image alternative
  rejected above.
